# unlp

自分が書いた日本語を出す際は、先に検出器で検査して指摘を直す。検出器は検出と採点だけを担う。指摘をどう直すかは、この手順と `reference/rules.md` の規則で判断する。

## 導入

```bash
cargo install --path .   # または配布バイナリを PATH に置く
unlp hook install
```

`hook install` は git の `commit-msg` hook を設置する。設置後は、コミットのたびにメッセージとステージした差分をまとめて採点するようになり、しきい値を超えたコミットは失敗する。何度実行しても結果は同じで、目印を持たない `commit-msg` が既にあるときは置き換えずに終了コード 1 で停止する。`unlp hook uninstall` は設置した hook を除去する。

Claude Code の hook からは `unlp diff --staged --fail-over 10` を実行する。コマンド文字列からメッセージを取り出せないので、メッセージの採点は git の hook に任せる。

### unlp.toml

`check` は最初のパスから、他の副コマンドはカレントディレクトリから上位に走査して最初に見つかったものを読む。`--config <path>` はそれより優先する。

```toml
threshold = 10
floor = 300
exclude = ["tests/**", "examples/**"]

[weights]
S01 = 3.0

[lists.S01.person]
add = ["監督"]
remove = ["相手"]
```

| 欄 | 内容 |
|---|---|
| `threshold` | 関門で超過とする 1000 字あたりの点。デフォルト値は 10 |
| `floor` | 正規化して採点する日本語文字数の下限。デフォルト値は 300 |
| `exclude` | 設定ファイルのあるディレクトリからの相対パスのグロブ。`*` は区切りをまたがず、`**` はまたぐ |
| `weights` | 規則 ID ごとの重みの上書き |
| `lists` | 規則 ID と欄ごとの語の追加と除外 |

`lists` の語は、欄ごとに照合する単位が決まる。表層で照合する欄（`phrases`、`words`、`conjunctions`、L01 の `idioms`、L02 の `compounds`）には、文の中に現れる文字列をそのまま記述する。原形で照合する欄（S01 の `person` と `speech`、L01 の `verbs` と `nouns`、L02 の `machines` と `terms`）には、辞書の分割単位の語を指定する。例えば `知らせる` のように辞書が分割する複合語は、追加しても一致しない。`remove` にデフォルトの語リストに無い語を書いても誤りにはならない。未知の欄名、未知の規則 ID、不正なグロブ、型の不一致は、ファイルのパスを添えた誤りとして終了コード 2 で止まる。

## 使い方

```bash
unlp check README.md src/            # ファイルとディレクトリ
unlp diff --staged                   # ステージした差分が触れた範囲
unlp diff HEAD~3..HEAD               # コミット範囲の差分
unlp commits -n 20                   # 直近 20 件のコミットメッセージ
unlp stdin < draft.txt               # 標準入力を 1 つの文書として
unlp stdin --format markdown < draft.md
unlp check src/ --json               # 機械が読む形式
unlp check src/ --summary            # 指摘を省いて集計だけ
unlp stdin --fail-over 10 < draft.md # 点が 10 を超えたら終了コード 1
unlp rules                           # 規則 ID、層、重み、規則集の見出し
```

`--fail-over` を渡さない限り終了コードは 0 で、指摘は出力に並ぶだけである。`hook commit-msg` は `unlp.toml` の `threshold` を読むので、関門の値をコマンドに指定しない。`--json` は `measures` に敬体率、常体率、和語率（名詞・動詞・文末の述語）、1 文あたりの「が」の数を出力する。

## 指摘を読んで直す手順

1. 指摘を受けた規則については、`reference/rules.md` の同じ規則 ID の節を参照する。見出しは `unlp rules` の一覧と一致する
2. 構造の層（S）から直す。指示でもモデルでも残る癖で、重みも大きい
3. 語彙の層（L）はどちらの極かを確認する。和語化（L01）と逐語訳（L02）で直す方向が反対になる
4. 密度・レジスター・定型句（D、R、F）は表層で直る。太字とダッシュは記法を外すだけで済む
5. G01 の列挙（文末の和語動詞と出現数）を受け取ったら、語ごとに慣習的なサ変動詞への置換を判断する。置換表は持たないので、分野の慣習に収まる `使う`、`決める` は残し、意味を文脈に預ける `引く`、`移す`、`落ちる` から置換する
6. D04 の件数（1000 字あたり）を受け取ったら、名詞と記号で済ませた説明を文に書き直す。具体例を添え、術語を定義し、変化と対比を文で述べる
7. 直したら同じ入力で再実行して、件数が減ったことを確かめる

下限（デフォルト値は 300 字）に満たない入力は、点を正規化せずに件数で判断する。構造か語彙の層の指摘が 1 件でもあれば関門は超過とし、密度・レジスター・語種の文書単位の規則は適用しない。コミットのメッセージと 1 件分の差分はほぼこの範囲に入るので、S と L の指摘を 1 件も残さない。

## 書く前の指針

- 文書・型・テストを語り手にしない。`README が述べる` は `README に書く`、`型が運ぶ` は `型に含まれる`
- 文頭の `これは` で前の文を受けない。`重要なのは`、`つまり、`、`正直に言うと` を置かない。`私` を出さない
- 術語は分野の慣習語にする。辞書の第一義（`既定では`、`静かに失敗`）も和語（`品書き`、`窓`、`電文`、`建てる`）も使わない。同じ文書では同じ語で通す
- 英語の比喩は抽象語に下げる。`無傷` は `変更しない`、`した瞬間` は `すると`
- 簡潔さは語数の少なさではない。助詞と主題を削って断片にしない。その行だけ読んだ人に通じる長さにする
- 譲歩と `ご指示ください` を毎回付けない。確信があれば言い切り、無ければ何が分かれば決まるかを書く
- 読み手が変われば骨格も変える。Slack の短報を PR 説明の圧縮版にしない
- 敬体と常体は読み手で決め、一つの文書の中で揺らさない
- 本文とコメントに太字、2 倍ダッシュ、矢印を入れない
- 文末の述語は分野の慣習語にする。`引く`、`移す`、`落ちる` で終わる文が並んだら和語化している
